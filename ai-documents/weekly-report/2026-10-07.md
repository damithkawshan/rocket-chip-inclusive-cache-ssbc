**The week's result: set balancing finally won on real applications. Two PARSEC/SPLASH programs
sharing a 256 KB L2 — memory traffic down 12.58%, and 29.5% of the damage the two applications do to
each other repaired. This is the first positive SBC result on anything other than our own synthetic
instrument.**

**The honest qualifier, stated up front:** the effect is real and the counters behind it are now
identity-verified, but we have **not yet proved it is a multi-application effect.** One
single-application arm looks *better* than the pair. Separating those two explanations is next
week's work and the experiment is already specified.

Audience: me and the supervisor. Covers 1–7 Oct; the previous week is in

## 1. The multi-application result

Two applications, each pinned, sharing one 256 KB 8-way L2 on the VCU118. One bitstream, migration
switched off and then on, same binaries and same inputs. LU (SPLASH-2, `-n512 -b64`) and
streamcluster (PARSEC).

| arm | n | memory accesses | hit rate | L2 accesses |
|---|---:|---:|---:|---:|
| LU alone, SBC off | 3 | 6,446,901 | 74.51% | 14,236,027 |
| streamcluster alone, SBC off | 3 | 1,390,328 | 92.12% | 15,242,430 |
| **both together, SBC off** | 3 | **13,650,286** | 72.80% | 33,180,357 |
| **both together, SBC on** | 2 | **11,933,076** | 76.32% | 33,117,542 |

**Memory traffic −12.58%. Hit rate +3.52 points. Misses per 1000 accesses 272.0 → 236.8 (−12.94%).**

### Running the two together costs a lot, and SBC gives some of it back

| | |
|---|---:|
| Traffic the two cause alone, added up | 7,837,229 |
| Traffic they actually cause together, SBC off | 13,650,286 |
| **Interference — the cost of sharing** | **5,813,058 (+74.17%)** |
| Same, SBC on | 4,095,847 |
| **Interference repaired by SBC** | **29.54%** |

So co-running inflates memory traffic by **74%**, and set balancing removes **just under a third** of
that penalty.

### Why this worked when omnetpp never did

This is the envelope rule from the 25 Sep work, holding on a real workload for the first time.
LU at `-b64` sits at a **74.5% hit rate** — it has overflow to move *and* the cache has somewhere to
put it. omnetpp at every geometry we can build has essentially no spare ways anywhere, which is why
five consecutive A/Bs came back at dead parity. **We did not change the design this week. We found
an operating point the design was always meant for.**

## 3. The measurement chain is now verified, not assumed

Last week's lesson was that a defect in a *counter* can look like a result. So before trusting the
headline I checked the counters against each other on the board's own data. These are identities that
must hold exactly if the hardware is counting correctly:

| identity | rows checked | result |
|---|---:|---|
| accesses = primary hit + secondary hit + data miss + upgrade miss | 34 | **exact, 34/34** |
| memory reads = data misses | 34 | **exact, 34/34** |
| memory reads − memory writes − clean evictions = 0 | 30 | **exact, 30/30** |

The third one closed the last open gap: `memWrites` previously had nothing to check it against, and
it now holds exactly across values spanning 186,748 to 6,539,253 — a 35× range, different workloads,
different geometries.

**A control run was added to test the measurement method itself.** Pairing LU with a do-nothing
program should make the pair's traffic equal LU's plus the do-nothing program's. Residual: **+14,762,
or 0.75%** of the total. So the subtraction that produces the interference figure in §1 carries under
1% of method error against a 12.58% effect.

## 4. A previously reported number is withdrawn

Chasing methodology, I audited every result file we have for a specific contamination: **more than
one migration-on measurement on a single boot.** Nothing in software can un-park a line or clear the
association table, so each migration-on run leaves the cache in a state that changes what the next
one sees. Only a full FPGA reprogram truly resets it.

| | |
|---|---:|
| Distinct sessions with more than one ON window | **8** |
| Worst single session | **36 ON windows** |
| FPGA reprograms, OpenSBI boots or reboots in that session's transcript | **0, 0, 0** |

That session is the ON half of the 72-run single-application sweep. Its runs were ordered by
configuration, so the contamination grows with position — which means **cross-configuration
comparisons in that table are invalid.** From a controlled experiment on 3–4 Oct (one ON window per
cold boot) we know the direction: warm runs read −13.1% / −10.0% where three cold boots of the same
point read −4.45% / −3.50% / −3.44%. **Contamination flatters SBC.**

**Consequences, stated plainly:**

- The **"−3.77% best single-application" figure is withdrawn.**
- The **"+60.79% worst case at b=32" figure survives** — it is a loss, and contamination would only
  have made it look better.
- **This week's pair result is unaffected.** All five pair sessions have exactly **one** ON window
  each, every one preceded by its own FPGA reprogram. I verified this per-session rather than
  assuming it.

A safety lock now refuses any plan that would put more than one ON window on a boot. It cannot be
overridden by accident.

## 5. Methodology hardening

I ran a deliberate flaw-hunt on the measurement harness rather than only on the RTL. Ten issues
found, by severity:

| fixed and tested | 7 — phase-order canonicalisation, the one-ON-window refusal, overlap gating, counter-identity gates, run-completion detection by unique token rather than shell prompt, negative-counter parsing, core-count enforcement |
|---|---|
| **evaluated and deliberately not fixed** | 2 — splitting the counter window would put a 737 KB statically-linked process *inside* it, which is worse than the problem. Documented with the reasoning |
| **found 7 Oct, still open** | 3 — all three block next week's campaign, all three are now prerequisites in its work order |

Three of these were caught because a result looked wrong and the harness, not the hardware, turned
out to be at fault. Two findings worth recording:

- A run was previously judged complete by seeing the shell prompt, which can match on a partial
  buffer. It now requires a unique per-run token.
- The counter parser used `[0-9]+`, so any **negative** counter value was silently dropped. One real
  counter does go negative.

## 6. What we cannot yet claim

Being explicit, because the result in §1 is tempting to over-read:

1. **It is not yet statistically significant.** Welch's t = 3.85, df = 2.00, **p ≈ 0.061** — just
   outside 0.05, purely because the off-side has n = 3. This is cheap to fix: the off-side parks
   nothing, so all repeats share one boot. n = 6 gives **p ≈ 0.003**.
2. **It is not yet shown to be a *multi-application* effect.** Single-application LU on its own read
   **−17.66%** — *better* than the pair's −12.58%. That arm is n = 1 and cross-session, so it is held
   open rather than believed, but until it is settled we cannot rule out that the benefit comes from
   the **operating point** (a 74.5% hit rate, which `-b64` produces with no second application at
   all) rather than from the interference.
3. **We cannot attribute traffic to an application.** There is one L2-wide counter block and nothing
   in the hardware carries a source or client id. So "streamcluster was protected from LU" is not
   currently measurable. Per-application evidence can only come from wall-clock time, which needs the
   dual-core run in §2.
4. **The headline is single-core.** Both applications time-share one core and genuinely share the L2,
   but they are not concurrent. The concurrent dual-core pair with migration on **timed out** and has
   not been measured.
5. **Speed, as opposed to traffic, barely moves here** — L2 cycles −1.31%, implying roughly **+1.33%**
   IPC. That is a property of the board, not of the design: the measured miss penalty is **27.9
   cycles** against 200–300 on a real part, so memory is only **10%** of runtime and any traffic
   saving is damped about **9.6×**. At realistic penalties the same traffic reduction projects to
   **3.9% (100 cycles)** to **7.7% (300 cycles)**. **Traffic and MPKI are the defensible metrics on
   this platform; IPC is not.**

## 7. Next week

The whole campaign is specified as two work orders, and the first is already finished.

| | Work | Cost | Why |
|---|---|---|---|
| 1 | **More off-side repeats** | 1 boot, no new code | p from 0.061 to ~0.003. The cheapest item on the list by a wide margin |
| 2 | **Aggressor dose-response curve** — sweep the co-runner's footprint across five intensities | 1 off boot + 5 on boots | **The deciding measurement.** If repair scales with interference, the multi-application story holds. If it is flat, the honest framing is "SBC helps low-hit-rate workloads". Both are results |
| 3 | **Self-pairs** (LU + LU, streamcluster + streamcluster) | 3 boots | Separates "two applications interfere" from "twice the pressure" |
| 4 | **A second victim** (`lu_cb`, same algorithm, different memory layout) | 2 boots | Tests whether the result is specific to one program's layout. Also settles the §6.2 confound |
| 5 | **Dual core with migration on** | 4 boots | The only route to a per-application claim. Starts at `b=128`, the geometry known to survive migration-on |
| 6 | **Two new co-runners built** — `radix` and `fft` | ✅ **done 7 Oct** | `radix` is the only available co-runner that is both high-miss and write-heavy like LU. `fft`'s strided transpose is the pattern set balancing exists for |

Item 2 is the one that decides how this work gets written up, so it goes first after item 1.

**Note on item 6:** both binaries are built and staged. The coder also found two errors in my own
sizing arithmetic — `fft` allocates **three** large arrays, not two, so `-m16` is 3 MB rather than
2 MB, and the padding knob has a second page-rounding step that makes it a no-op below `-m14`. Both
corrected in the work order before any board time was spent on them.

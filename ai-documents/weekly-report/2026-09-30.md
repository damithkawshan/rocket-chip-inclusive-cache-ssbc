## 1. We reached the paper's operating point

Until now every one of our measurements used an **8 kB L1**. The paper uses **32 kB**. That matters more
than it sounds: a big L1 absorbs the easy hits, so the L2 only sees the hard accesses. A small L1 passes
easy traffic through and flatters the L2's hit rate. We had been comparing different things.

With the L1 corrected and the L2 within 2× of the paper's:

| omnetpp, L2 miss rate | |
|---|---|
| Paper — 2 MB 8-way, 32 kB L1 | **28%** |
| **Us — 1 MB 8-way, 32 kB L1** | **24.58%** |
| Us earlier — 128 KB, 8 kB L1 | 16.6% |

**This is the closest we have ever been to the published setup**, and the numbers line up.

## 2. And set balancing still did nothing

Same binary, same amount of work, one bitstream, migration switched off then on:

| | OFF | ON | change |
|---|---:|---:|---|
| hit rate | 75.42% | 75.35% | **−0.07 points** |
| time (L2 cycles) | 356,724,253,178 | 356,689,654,057 | **−0.010%** |
| memory reads | 1,213,260,236 | 1,215,468,242 | **+0.182%** |
| memory writes | 514,664,870 | 514,721,766 | **+0.011%** |

Dead parity, for the fifth time.

### What the counters say happened

- **617,145 lines were moved. Two were still parked at the end.** The steady state is roughly zero.
- Each moved line served **0.34 hits** before being destroyed (break-even is 1.0).
- **0.004%** of all accesses were served from a moved line.
- **93.3%** of the extra searches found nothing.
- Arithmetic implies **44% of moves overwrote another moved line** — pure churn.

So the machinery works; it simply has nowhere useful to put anything. That is the envelope rule again:
omnetpp has essentially no spare ways anywhere, at any cache size we can build.

### One caveat that must be fixed before this is quoted as final

This run was **dual core**, and **96.7% of the 669,562 failed moves failed because the other core's L1
was holding the destination line**. That is the one case (012 C3) we deliberately did not build, because
it deadlocked the board in September. A **single-core re-run is owed** before judging SBC at this
geometry. The bitstream already exists.

## 3. The defect we found: the migration decision is being fed the wrong events

SBC decides everything from one small counter per set — the **saturation counter** (+1 on a miss, −1 on
a hit). A set migrates out when its counter is at maximum, and accepts lines when its counter is low.

That counter has one input, and it is wired to **every** directory lookup, not only to real CPU
requests. So when an L1 writes a line back, the L2 looks it up, finds it, calls it a **hit**, and
**cools the set by one** — even though nothing good happened to that set. A cooled set then looks like a
good place to send someone else's overflow.

| | |
|---|---:|
| Directory lookups feeding the counter | 6,270,326,354 |
| Actual CPU requests among them | 4,931,117,515 |
| **Events that should never have counted** | **1,339,208,839 — 21.4%** |

**Why this matters for the whole project:** it hits write-heavy programs hard and read-only ones barely.
omnetpp wrote back 514 million dirty blocks; our synthetic instrument `l2_miss_calib` wrote back a few
thousand. **So the tool we validated the design with is almost unaffected, and the real workload is
heavily affected.** Part of the gap between "the synthetic test says −41%" and "the real program says 0%"
is therefore a measurement defect, not only a difference in the programs.

The fix is four small edits following a pattern already used seven times in the same file, plus one
design decision. It is testable in simulation before any FPGA build, and it makes a **falsifiable
prediction**: it should change omnetpp's behaviour a lot and the synthetic test's hardly at all.

## 4. The envelope rule survived two more geometries

| | 64 KB / 16-way (64 sets) | 64 KB / 8-way (128 sets) | 1 MB / 8-way (2048 sets) |
|---|---:|---:|---:|
| Points where SBC won | 50.0% | 66.2% | **72.3%** |
| Best case | −41% cycles | −46% | **−49%** |
| **Worst case** | **+13.6% cycles** | +5.0% | **+3.3%** |

More sets and fewer ways make the design much safer: the worst case falls from +13.6% to +3.3%.

⚠️ **These sweeps must not be over-read.** The synthetic test fixes the per-set overflow by construction,
so scaling the cache does not change the workload's shape — which is exactly what *does* change for a
real program. They say "if a workload has this shape, SBC helps at any size", not "a real workload will
have this shape".

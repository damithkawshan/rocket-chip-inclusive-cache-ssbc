## What the design is trying to do

- A cache stores each memory address in one fixed group of slots, called a **set**
- Real programs do not spread evenly: a few sets get hammered while others sit nearly empty, so busy
  sets keep evicting useful data while capacity goes unused next door
- The Set-Balancing Cache **moves a line out of an overloaded set into an idle one** instead of
  throwing it away
- Phase 2 built the moving machinery. **Phase 3 — the part that actually produces a speedup** — will
  look in the partner set on a miss and serve the line from there instead of going to main memory

## The situation before this work

- Phase 2 was marked complete but was effectively inert
- Migration fired roughly **once in every 5,500 opportunities**
- A long-standing assertion failure crashed the heaviest test
- Phase 3's payoff scales directly with how often migration happens, so none of it could be justified
  until that rate came up

## What we found and fixed

Three bugs, in order. Each had to be cleared before the next became visible.

### 1. The cache was refusing to move almost everything

- **Cause:** before moving a line, the L2 checks whether the CPU still holds a copy. That record was
  almost always wrong — the L1 quietly discards clean lines without telling anyone, so the L2
  believed the CPU was using lines it had long since dropped. **99.7% of candidates were rejected on
  this one stale bit**
- **Fix:** ask before deciding. A normal eviction already sends a message to the CPU to reclaim the
  line, so send that first and then decide. The information is free because we were already paying
  for it
- **Outcome:** migration rate ~0.02% → ~78%

### 2. The destination was chosen far too early

- **Cause:** we picked the target set at the start of a request, then acted on it many cycles later.
  Everything in between was a gap in which another request could claim the same set. Four separate
  pieces of bookkeeping and a guessed eight-cycle timer existed only to paper over that gap
- **Fix:** read the destination at the moment it is used, and claim it in the same cycle. The gap
  becomes zero rather than merely short
- **Outcome:** fixed the long-standing crash; deleted 4 state elements and the timer

### 3. Half of all completed migrations were being thrown away

- **Cause:** the tracking unit announced it was free for new work while a migration was still
  finishing, so it was handed the next request and reset mid-flight. One line — an earlier change had
  added a guard to the "finished" condition but missed the matching "ready for more work" condition
  beside it
- **Consequence:** usually only the bookkeeping was lost, but that bookkeeping is the table Phase 3
  uses to find moved lines. Occasionally data was copied without the directory being updated, which
  is a genuine correctness bug
- **Outcome:** dropped migrations 94 → 0

## Why this matters for the next phase

- **The association table is correct for the first time.** It records where each moved line went, and
  Phase 3 finds moved lines by consulting it. Until now roughly half of all moves were never
  recorded, so those lines would have been permanently unfindable
- **The migration counter can be trusted.** It had been under-reporting by about half, which means
  earlier rate measurements were wrong
- **Migration now happens often enough to be worth exploiting** — the standing precondition for
  starting Phase 3

## Next steps

1. **Apply the same fix on the receiving side.** Roughly 99% of attempts are still turned away when
   checking the destination set, using the identical stale record that fix 1 corrected on the sending
   side. Clearest remaining win
2. **Re-measure on a realistic workload.** Current numbers come from a correctness test, which is not
   representative of read/write behaviour in real programs
3. **Begin Phase 3.** Search the partner set on a miss and serve the line from there instead of going
   to memory

## Note on method

The third bug was found the slow way. It came from a previous change that added a guard in one place
and missed an identical spot beside it — comparing the modified code against the original version
would have exposed it in under a minute. Instead it took several rounds of simulation instrumentation,
each costing about ten minutes, pursuing an incorrect theory. **Comparing against the
pre-modification code before instrumenting is now the first step whenever this subsystem
misbehaves.**

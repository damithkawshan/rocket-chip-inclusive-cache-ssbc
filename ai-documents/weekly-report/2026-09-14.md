## Headline

For the first time the design ran on the FPGA board, under Linux, on a SPEC CPU2017 benchmark
(`520.omnetpp_r`), with set balancing **on and off doing exactly the same work**.

**Set balancing makes the cache slower: the run takes 32–51% longer and goes to main memory 2.5–7
times more often.** The data stays correct. Three separate tests on two cache sizes agree on the
direction. Each test ran once, so the exact size of the loss is not final.

## What we did

1. **Measured the hardware cost (8 Sep).** The L2 cache grows by 157% in logic, but the whole design
   goes only from 5.2% to 6.1% of the FPGA. The timing cost is 0.47 ns of a 20 ns clock (about 2.5%).
   Area is not a concern at this size.
2. **Ran the first board test (10 Sep).** With a fixed 10-minute window the hit rate was 90.2% off and
   66.1% on. While checking it we found that the hit counter also counts traffic that is not a CPU
   request, so both numbers are inflated.
3. **Built tools for a fair test (11 Sep).**
   - A runtime **on/off switch**, so both halves of a test run on the same chip image. Checked: the
     "off" half scored 90.19%; a separately built image without the feature scored 90.24%.
   - Counters for **trips to main memory**, and a **cycle counter** inside the cache. The board does
     not let software read the CPU's own cycle and instruction counters, so the cache counts time itself.
4. **Found that a fixed time window gives the wrong answer (11 Sep).** In the same 10 minutes the "on"
   half got through about 20% less of the program. Fewer memory trips then looked like a win, when the
   machine had simply done less. We switched to **fixed work**: run the benchmark to a set simulated
   time, and measure until it ends.
5. **Ran fixed-work tests (11–13 Sep).** Three finished. Five longer attempts did not finish within a
   board session — omnetpp first builds a large simulated network, and at 50 MHz that alone takes hours.
6. **Tidied the research documents (14 Sep):** grouped them into folders, and added a task status
   tracker, a list of what the build phases left behind, and a guide to the cache's "who goes first" rules.

Also since the last report (1–4 Sep): total hit and miss counters; the paper's "partner may hold my
line" bit, which skips useless searches; moved lines placed last in line for eviction; a counter-only
reset register; and the guide for running the design on the board under Linux.

## Why it is slower — what we believe, not yet proven

- **Moved lines pile up and crowd out ordinary lines.** In one session they grew from 825 to 1,804 of
  the cache's 4,096 slots, and the hit rate fell from 79% to 62.5% as they grew.
- **Moved lines are used, but far less than ordinary lines.** Each moved line is reused about 120 to 290
  times before it leaves — well above break-even — yet per slot it does about 13 times less work than an
  ordinary line.
- **Two eviction rules make it worse.** Moved lines are always evicted last, so they rarely leave. And
  when the random pick lands on a moved line, the cache falls back to the first ordinary slot every
  time — about 44% of evictions stop being random.
- **Our cache evicts at random; the paper's evicts the least recently used line.** Under that rule a
  moved line's head start fades on its own. Under ours it becomes permanent.
- **Found this week while checking the design against the code:** nothing ever ends a pairing between
  two sets, and a line served from its partner set counts as a *miss* for the home set's "heat" — so a
  set that is being helped still looks like it needs help.

## Reported plainly

- Every number is from **one run**. Repeats come next.
- The cycle counter is the cache's own clock; whether it is the CPU's clock is not confirmed. The on/off
  comparison is fair either way.
- Hit rates still count some traffic that is not the program's, so we quote time and memory trips instead.
- The event counters are 32 bits and would overflow on longer runs. Widening them to 64 bits is in progress.

## Note on method

**A test that looks fair can flip the sign of the answer.** The fixed 10-minute window compared two runs
that did different amounts of work, and on memory trips it would have shown set balancing as a win. The
rule now: compare only runs that did the same work, and check the work count before reading any other
number.

A second lesson: the three finished tests were recovered from board session logs that no document had
recorded. Write up every board session the same day.

## Change 1 — late destination binding (`f40fbd4`)

**The problem:** we picked a destination set at allocate, then used it many cycles later. Everything
in between was a hole — another request could take that set.

**The fix:** read the destination at the moment the migration actually starts, and claim it in the
same cycle so the fence sees it immediately.

**Deleted:** `migAdviceDstReg`, `migTokenPending`, `migTokenDstSet`, `migPendCtr` and the guessed
8-cycle timer. All of them existed only to survive that hole.

**It also fixed `assert (new_meta.hit)`** — the long-open case-7 crash. That confirms the standing
hypothesis: the crash came from the widened `[born → gate]` window.

**Two traps hit during implementation** (both caught by elaboration, both worth remembering):

1. The claim wire must not touch `io.allocate.valid` **or** `io.allocate.bits.*`. Both are
   combinationally tied to `allocReady`, which the claim feeds. Spell the fast-path condition out
   from `io.directory.bits` / `request` instead of `new_meta` / `new_request`.
2. The destination offer must mask "another migration in flight" **per MSHR**, not globally. A
   deferred migrant raises `migPending` itself, so a global mask takes the offer away from exactly
   the MSHR that needs it — every deferred migration would have declined silently.

**Approved policy:** decline-and-skip. If no destination is available at the decision point, skip the
move and do a plain eviction. Never re-pick, never stall. Measured cost: **470 declines out of 39,572
starts** — cheap. Escape hatches, if it ever underperforms, are written up in `phase-3.md`.

## Change 2 — the reload bug (`707445c`)

**One line.** Upstream had these two agreeing:

```scala
io.schedule.bits.reload := no_wait     // "give me the next request"
when (no_wait)              { ... }    // retire
```

Phase 2 added the migration gate to **retire** but not to **reload**:

```scala
io.schedule.bits.reload := no_wait                  // ← missed
when (no_wait && mig_ready) { ... }                 // ← gate added here only
```

So an MSHR advertised itself free while a migration was still finishing. The Scheduler started a
directory read for the next request, and that result hit the eviction-assess reset — wiping the MSHR
**without retiring it**.

**Three symptoms, one cause**, depending on whether dir-write #1 had gone out:

- **already out** → only the `migCommit` pulse lost → **the AT is never written** (a hard Phase-3
  blocker: the secondary search finds displaced lines via the AT) and `SBC_Migrations` undercounts ~2×
- **not yet out** → destination data overwritten under a stale directory label, and the pending
  refill dir-write #2 cancelled too
- and it was **the cause of the case-5 regression**

Fix: `io.schedule.bits.reload := no_wait && mig_ready`, plus a one-line assert at the assess-reset so
it cannot silently return. Bit-exact with baseline when SBC is off.

## Method lesson (this one cost real time)

The bug was a Phase-2 change that added a gate in one place and missed a sibling.

**`git show <pre-SBC>:file` and comparing every consumer of the touched signal found it in 30
seconds — after several 10-minute instrumented sim cycles chasing a wrong theory.**

The wrong theory: "94 copies completed but never committed, therefore 94 corruptions." That framing
was committed to before checking `s_dmeta`, and two written reports were built on it. In fact 93 of
the 94 were harmless to data. **When SBC-era logic misbehaves, diff against upstream before
instrumenting.**

A second useful move: the elimination run. Instrumenting the *passing* baseline showed it hit the
"corrupting" variant **twice** while the *failing* build hit it once — killing that suspect by
measurement rather than argument.

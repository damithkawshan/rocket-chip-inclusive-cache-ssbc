# Daily summary — 2026-08-18

**Branch:** `set_migration_refactored`
**One line:** We found out *why* migration almost never happened, fixed it, and migration went up
about 7,200 times. It is not finished — one test still fails.

---

## 1. Where we started

Phase 2 was signed off yesterday. But one number was bad:

- Out of 129,488 chances to migrate a line, migration happened **9 times**.
- Phase 3's whole benefit depends on that number. At 9, there is nothing to build on.
- We did not know the cause. The plan said "go and measure it".

## 2. What we found out

**We did not need to build anything to find the cause.** The log already printed the reason for every
rejected line. We just had never counted them.

Out of the evictions where migration was allowed:

| Reason we said no | Share |
|---|---|
| "The L1 still has this line" | **99.7%** |
| "The line is dirty" | 0.26% |
| Nothing — we migrated | 0.02% |

So it was never about dirty lines. It was about the "L1 has it" bit.

**Then we found that bit is usually a lie.** Rocket's L1 throws away clean lines **without telling
the L2**. That is a default setting (`silentDrop = true`). So the L2's note stays set forever until
something asks.

The proof: the L1 can only hold 4 lines. About 32 lines were marked "L1 has it".

## 3. The idea we came up with

Ask the L1 before giving up. That question is called a probe.

**The important part: we were already sending that probe.** A normal eviction of a client-held line
probes the L1 anyway. We were just throwing the line away *before* reading the answer.

So the change is not "add a probe". It is **"move the decision to after the probe we already send"**.

## 4. What we built

- The eligibility test is now split in two: decide what we can up front, probe, then decide the rest.
- A line that is already free still migrates immediately, with no probe (unchanged, still free).
- If the probe comes back with data, the line is dirty now, so we fall back to a normal eviction.

We also had to hold the memory fetch back during the probe. **That gate is not optional** — without
it the cache fetches the new line early and writes it on top of the old one, and separately it
deadlocks (the scheduler fires all requests together, so the stuck fetch would also stall the probe
that was the only thing able to unstick it).

## 5. The result — the idea works

| | Before | After |
|---|---|---|
| Migrations started | **9** | **65,109** |
| Success rate of the eligibility test | 0.018% | **78.4%** |
| Migrations completed | 6 | 63 |

Of 57,853 lines that the old rule rejected, **57,845 probes came back clean.**
That is **99.99% of those bits were lies**. Only 8 were really dirty.

Bonus: the displaced-reclaim path fired 84 times. Before today it had never fired in a normal run —
we had only ever forced it. That evidence is no longer synthetic.

## 6. Two bugs we hit and fixed on the way

1. **A hang.** The cache marked the memory fetch "done" without ever sending it. Cause: that
   bookkeeping copied the gate condition by hand instead of using the real signal, so it drifted the
   moment we added a term. Fixed by using the real signal — it cannot drift again.
2. **An impossible directory entry.** A parked copy was written as "one client owns this" while we
   had cleared its client list. Old code never hit this, because client-held lines never used to
   reach the migrate path. Fixed by downgrading the state, the same way the ordinary path does.

Neither was on our risk list. Both come from the same thing: rules that only held because the old
test was so strict.

## 7. What is still broken — pick this up first

**6 of 7 tests pass. The 7th fails** with: an L1 returns a line that the L2 has no record of.

Our best guess, and we predicted it in the design doc: the destination set is only protected once the
migration commits. That now happens a whole probe later, and the old 8-cycle guard expires in the
middle. So another request can slip onto the destination set and get overwritten.

**Proposed fix:** do *not* protect the destination earlier (that risks deadlock). Instead, at the
moment the probe clears, check that nobody else is using the destination set — and if somebody is,
just do a normal eviction instead. Declining costs nothing and cannot deadlock.

## 8. The other big finding — the bottleneck moved

```
Migrations started    65,109
Died at destination   64,985   <-- 99.8%
Completed                 63
```

The destination check asks the **same "does a client have it" question** — and reads the **same stale
bit**. So we fixed one side and immediately hit the same problem on the other side.

That is why starts went up 7,200× but completions only 10×.

**So the next real question is the destination side, not the Phase 3 swap.** Do not start building
the Phase 3 datapath yet.

# 2026-08-28 — Two diagnoses tested and killed; one real defect fixed; the corruption is still open

## 2. Hypothesis 1 — the wrong partner set. **DEAD.**

**The claim.** The pairing lookup is keyed to the request waiting at the input port, broadcast to
every MSHR, and latched by any MSHR whose allocate is not a tag-`repeat`. Since `repeat` is a **tag**
test being used to decide whether the MSHR's **set** changed, an MSHR on set X could latch set Y's
partner and search there. In this benchmark `set_addr(s,t) = DRAM_BASE + t*512 + s*64`, so the tag is
a function of `t` alone and identical in every set — a search in the wrong set still tag-matches.

**The gate.** Compare the distinct `(srcSet, dstSet)` pairs from `MIG-COMMIT` (the true pairings)
against the distinct `(set, partner)` pairs from `SEC-HIT` (what searches actually used).

**Result: identical.** Both are exactly `{1→3, 5→7, 6→0}`.

| check | finding |
|---|---|
| every search, hit or miss (62,983) | still exactly `{1→3, 5→7, 6→0}` |
| who searched | only sets 5, 1, 6 — precisely the three paired sources. No unpaired or destination set ever searched. |
| where served bytes came from | `SEC-COPY-DONE`: every repatriated block read from the correct partner |

The printf reads `pairSetReg` directly ([MSHR.scala:1026](../../design/craft/inclusivecache/src/MSHR.scala#L1026)),
so this is the latched value itself, not an inference. With three pairings whose partners are all
distinct, a mis-latch could not have hidden.

## 3. Hypothesis 2 — skipped searches create stale twins. **DEAD.**

**The claim.** The design rests on an invariant stated in [diagram.md:204](../diagram.md):
*a refill only ever happens after the partner was searched and found empty of the line.* If a search
is skipped, we fetch from DRAM while a copy is still parked → two copies of one address → the
parked one goes stale when the native one is written → a later search serves the stale version.

**Gate A — the count comparison (the one the task specified).**

| set | demand misses | searches | gap |
|---|---:|---:|---:|
| 1 | 19,728 | 19,657 | 71 |
| 5 | 23,724 | 23,686 | 38 |
| 6 | 19,682 | 19,640 | 42 |

151 unsearched misses — which reads as confirmation, **and it is wrong.** The coder found the
confound the task had not considered: a set has no AT entry until its first `MIG-COMMIT`, so a miss
before that point correctly runs no search and has nothing parked to find. Replaying the event stream
in order and splitting on each set's first commit:

| set | unsearched **before** pairing | unsearched **after** pairing |
|---|---:|---:|
| 1 | 71 | **0** |
| 5 | 37 | **1** |
| 6 | 42 | **0** |

**One** post-pairing sighting in **60,169** misses — 0.0017%. The hypothesis predicted the opposite
("on a hammered hot set, most misses take that path"). 99.998% of post-pairing misses did search.

**Gate B — the direct test, and this is the one that decides.**

`DIR-WRITE` is printed unconditionally on every directory write
([Scheduler.scala:181](../../design/craft/inclusivecache/src/Scheduler.scala#L181)), so the full
directory can be shadow-modelled from the log. 1,667,711 `[SBC]` lines replayed from reset.

A **twin** = the same tag simultaneously native in a paired source and displaced in its partner.

| | count |
|---|---:|
| **native-side twins** (a line refilled while a parked copy was already live) — the failure mode claimed | **0** |
| parked-side (a displaced copy installed while still native) | 22,156 |

**Why the zero is trustworthy** — a detector reporting zero needs a positive control and an
opportunity count, and it has both:

- **Positive control:** the parked-side branch is the exact mirror — same shadow directory, same tag
  matching, same pairing map — and fired 22,156 times. All 22,156 are the migration's own two-write
  sequence: median 3 log lines of coexistence, max 11, 100% resolved, none open at end of run.
- **Opportunity count:** a line was installed natively into a paired source **49,452** times while
  that partner held parked lines (mean 3.06 of 8 ways). The native-side branch was evaluated 49,452
  times with a non-empty parked set and never matched.

Chained to the symptom: **0 of the 3,268 `SEC-HIT`s served a copy that had ever been twinned.**

**The `diagram.md:204` invariant holds in this run** — 0 violations in 60,169 post-pairing misses.

## 4. What landed — `0f5a7ac` (C1 + C3)

The latch defect is real *as a defect* even though it explains nothing. It was fixed for its own
sake, because it is rare for a **geometry** reason rather than a structural one: the harmful branch
needs a paired source to be unowned at the moment of the mis-latch, and at 8 sets under a hammer they
almost never are. Task 003 moves to a larger geometry and this should not be in the RTL when it does.

**C1** — the pairing question is now asked about the MSHR receiving a directory result
(`Mux1H` over `directoryFanout`, the pattern `destQuery` already used) instead of about whatever is
waiting at the port.

**C3** — assert in the Scheduler that a paired source never issues an outer Acquire without having
searched. Deliberately built on a *separate* assert-only AT read (`checkQuery`/`checkIsSource`) keyed
to the scheduling MSHR's own set, so it never passes through `pairValidReg`/`pairInfo`/`assocQuery` —
**if C1 were wrong, C3 would still fire.**

**C2 deferred** — see §6.

### Acceptance

| | before | required | actual |
|---|---:|---:|---:|
| unsearched post-pairing misses | 1 | 0 | **0** ✅ |
| unsearched pre-pairing misses | 150 | ~150 | 234 ✅ * |
| wrong-partner searches | 0 | 0 | 0 ✅ |
| native-side twins | 0 | 0 | 0 ✅ |
| parked-side control | 22,156 | — | 21,893 (detector live) |

\* per set unchanged (1: 71→69, 5: 37→37, 6: 42→45). The extra 83 is set 4's own pre-pairing window,
which exists only because a fourth pairing formed. Correct by definition.

`MSHR.scala:915` did not fire. Nor did C3, nor any other — **21,897 migrations, 84,691 searches,
0 SBC asserts.**

### ⚠️ `case_full_dirty_dst` now PASSES. Do not record this as a fix.

The stress result moved 5/7 → 6/7. **It is perturbation, not repair**, and treating it as a fix would
hide the defect and narrow the hunt wrongly.

| | before | after |
|---|---|---|
| pairings | 1→3, 5→7, 6→0 | **4→3**, 5→7, 6→0, 1→2 |
| migrations into set 3 | 2,355, sourced from set 1 | 1,723, sourced from **set 4** |

`case_full_dirty_dst` is the "full dirty cold set 3" case. **The set paired into set 3 changed
identity.** The latch fix shifts which MSHRs search and when → DSS timing shifts → the whole map
reshuffles. Reinforced by the acceptance number: the fix removed **one** unsearched miss in 60,169.
One event cannot be the difference between a reproducible corruption and a clean pass.

**A PASS obtained by perturbation is worse than a FAIL** — it removes the repro without removing the
defect. `sbcForceDstSet` exists precisely for this: pin destinations to recreate a map where set 3's
source is set 1 again and see whether case 4 fails. That settles it by measurement instead of
argument.

`case_reaccess_migrated` still fails. The repro is intact.

## 5. The live lead — A5, and it is the coder's original one

Both details supplied to the coder were confirmed as literal facts about the RTL:

- **The SCU can stall mid-block.** [SetCopyUnit.scala:137](../../design/craft/inclusivecache/src/SetCopyUnit.scala#L137)
  re-evaluates `copy_wsafe` on **every write beat**, and `wrBeat` advances only on `bs_wadr.fire`. A
  drop mid-block leaves some beats new and some old. Nothing latches the safety decision for the
  duration of the block.
- **`copy_wsafe` is one cycle behind.** [SourceD.scala:406](../../design/craft/inclusivecache/src/SourceD.scala#L406)
  guards the `s1` comparison with `busy`, a register — but SourceD issues its first bank read from
  `io.req.bits` in the cycle `io.req` fires, while `busy` is still false and `s1_req_reg` still holds
  the previous request. The comparison is one cycle behind the read it guards.

This blind spot is **upstream's**, shared by `evict_safe` and `grant_safe`, and the comment at
[SourceD.scala:378](../../design/craft/inclusivecache/src/SourceD.scala#L378) reads as an
acknowledged approximation. Upstream is safe because *"the first cycle of SourceD falls within the
occupancy of the MSHR's plan"* and because a copy's destination is a **fenced cold set**. A
repatriation writes into `request.set` — this MSHR's own **live** set. That is the assumption being
used outside its conditions.

**The open question, and it is the right one:** *who actually reads `(request.set, meta.way)` while
the SCU writes it?* The MSHR's own Grant is gated behind `w_scopy`, its release path behind
`w_releaseack && w_rprobeacklast`, and set exclusivity should keep other MSHRs off. If none of those
is the reader, the hazard is unreachable and A5 is the wrong tree too.

**Next action:** a check in the BankedStore — the one module that sees every port — that fires if
anything else touches the destination location while a repatriate copy is in flight, and **names the
port**. Sim-only, one run, answers the question directly instead of theorising.

## 6. Two defects in the work order itself

Both caught by the coder before they shipped. Recorded because the instruction was wrong, not the
implementation.

**C1 as written was incomplete, and the missing half would have made things worse.** `searching` is
armed in the plan block, which runs in the **same cycle** as `io.directory.valid`. Moving the latch
there while leaving the consumer on `pairValidReg` would arm searches off the *previous* directory
result's pairing. The landed form arms off a live `pairLive = io.directory.valid && io.pairInfo.valid`;
the register survives only to carry `pairSetReg` forward to the dread/copy/erase.

**C2 as specified was incorrect, not merely disruptive** — and it is the same one-cycle hazard.
`migFastWantW` reads `migAdviceValidReg` **combinationally** in the `io.directory.valid` cycle
([MSHR.scala:825](../../design/craft/inclusivecache/src/MSHR.scala#L825)), so latching there delivers
it a cycle late and the migrate fast path stops working. The correct form is to **delete** the
register, not move it — once the query is keyed to the asker, the advice wants to be a live wire.
Deferred rather than bundled, because that changes MIG-DEFER behaviour on the repeat-allocate path
([MSHR.scala:1071](../../design/craft/inclusivecache/src/MSHR.scala#L1071)), which is reachable
(`final_meta_writeback.hit` can be false with a non-INVALID state), and a migration-behaviour change
bundled into C1 could not be bisected apart.

C2's premise was also partly moot: the demand-A filter it proposed moving into the MSHR is **already
applied there** from the MSHR's own request ([MSHR.scala:828](../../design/craft/inclusivecache/src/MSHR.scala#L828)).
Only the `hot` term is mis-keyed.

## 7. Post-mortem on the analysis — read this before trusting the next theory

Three diagnoses were put forward today and the day before. **All three were wrong.** The pattern is
consistent enough to be worth writing down.

**What was reliable.** Every *structural* claim was confirmed at the cited line: the pairing
mis-keying is real, the SCU stalls mid-block, `copy_wsafe` is a cycle behind. Reading what the RTL
*is* worked.

**What was not.** Every *timing and reachability* claim was wrong — "is this signal valid this
cycle", "does this path actually occur", "how often does this fire". Those were wrong every time.

**The three failure modes:**

1. **"A defect" was treated as "the defect."** A genuine bug was found, a story was built connecting
   it to the symptom, the story was internally consistent, and that was mistaken for evidence. The
   pass/fail pattern already contradicted it — cases 1 and 2 are loads-only and passed — and was not
   checked.
2. **Attachment, then fitting.** When gate 1 killed the theory, the search continued for another
   consequence of the *same* defect rather than starting fresh. Theory 2 was fitted to the pass/fail
   pattern. **Fitting is not predicting** — a story built to match evidence always matches.
3. **Structure reasoned about without timing.** C1 moved a register write without tracing when every
   consumer reads it — after "a gate added in one place and missed in its sibling" had been written
   into that same task document as trap 1.

**What worked, every single time: the gates.** Two log-based gates and one bisect. Every real advance
today came from a measurement, not from analysis.

**Process rules adopted:**

- Propose **experiments and invariants**, not mechanisms. The coder derives timing.
- Test any theory against evidence already in hand **before** putting it forward.
- Any fix that moves a register must enumerate every reader and its cycle — or say so explicitly and
  hand that derivation over.
- State a falsifiable prediction **before** the run, not an explanation after.

## 9. Also learned today

**Destination turnover is a real capacity finding, not a bug.** The `6→0` pairing showed 255 hits
against 19,138 migrations, against near-1:1 for the other two. Explanation from the log:

| destination | lines parked in | reclaimed out |
|---|---:|---:|
| 0 | 19,138 | **18,881** |
| 3 | 2,355 | 2 |
| 7 | 666 | 4 |

Set 0 absorbed 19,138 parked lines into **8 ways**; 98.7% were reclaimed before set 6 came back for
them, so those searches correctly find nothing. **One pairing cannot absorb a hot set's whole miss
stream.** The paper's associations hold ~2.15 lines and then dissolve; ours absorb thousands because
teardown does not exist yet. That is a concrete argument for teardown being load-bearing rather than
an optimisation.

**A reusable asset:** the log-replay shadow directory is config-independent — it reads `DIR-WRITE`
lines. Re-running either gate on any future log is a grep, not a re-derivation.

## 2026-09-30 — benchmark validity, page coloring, and the missing destination throttle

### Verified from source (not recalled)
- SPLASH-2 FFT is deliberately padded against conflict misses. `codes/kernels/fft/fft.C`
  header: "4) Matrix data structures are padded to reduce cache mapping conflicts".
  `pad_length` computed from `line_size` and `PAGE_SIZE` (~:212-229), threaded through
  ~20 sites as `j * (rootN + pad_length)`. NOT disableable from the CLI — `-lL` only
  scales it. Zeroing it is a one-line source edit.
- PARSEC's own 13 are NOT padded the same way. `streamcluster` uses
  `tbb::cache_aligned_allocator` + `CACHE_LINE 32` = FALSE-SHARING avoidance, a
  different problem; it does not reshape the set distribution. `canneal` is
  deliberately cache-hostile (random netlist pointer chasing).
  => The padding problem lives in the SPLASH half of PARSEC 3.0, not the PARSEC half.
  (SPLASH verified line-by-line; PARSEC side is a spot-check + design philosophy.)

### 🔴 Page coloring — likely the real reason omnetpp shows no imbalance
Already documented in our own sw/l2_miss_calib.c:10-14:
  set = ((frame << 6) | (o >> 6)) & (sets - 1)

At 1 MB / 8-way / 2048 sets / 64 B lines / 4 KB pages:
  set index   = PA[16:6]  (11 bits)
  page offset = PA[11:6]  ( 6 bits) -> a page reaches only 64 sets  [program controls]
  frame       = PA[16:12] ( 5 bits) -> 32 page groups               [LINUX controls]

So 5 of 11 set-index bits belong to the page allocator. `pad_length` can only ever
touch the other 6. Consequences:
  1. Editing pad_length does NOT deterministically create set imbalance here.
  2. Linux frame allocation is itself a set-spreader -> candidate explanation for
     omnetpp's absent exploitable imbalance at 2048 sets. TESTABLE.
  3. This is exactly why l2_miss_calib needs root + /proc/self/pagemap + MADV_NOHUGEPAGE:
     it hand-picks frames in one group. Real workloads cannot.

### Proposed experiment (cleaner than a benchmark mix)
2 MB hugepage -> offset PA[20:0] CONTAINS the whole set index PA[16:6], so the program
regains full deterministic set control and pad_length works as its 1995 authors intended.
Three points, one program, one variable:
  | hugepages + padded FFT      | program, conflict-free  | baseline, SBC idle |
  | hugepages + pad_length = 0  | program, pathological   | SBC best case      |
  | 4 KB pages, either          | OS launders 5 of 11 bits| realistic middle   |
Claim it supports: "SBC recovers in hardware what hand-padding buys in software."
That is Seznec's skewed-cache argument, and it is a mechanism/sensitivity result that
must sit NEXT TO unmodified benchmarks, never instead of them (otherwise it reads as
benchmark-tuning and gets rejected).

### Reasoning correction (mine, recorded)
"Multicore sharing defeats the padding and re-creates imbalance" is not the mechanism.
If padding made A uniform and B uniform, A+B is still uniform — more pressure, not more
imbalance. Mixes work by SUPERIMPOSING TWO ALREADY-NON-UNIFORM profiles, widening the
hot-cold spread. Real programs are non-uniform by default: V-Way's motivating figure was
on SPEC CPU2000, which nobody padded.

### Mixes push BOTH envelope terms the wrong way
Envelope is `overflow <= spare`. A co-runner raises overflow AND consumes the spare ways
in the cold sets. 1 MB shared two ways is ~512 KB each. Already measured: the 2026-09-26
dual-core run had 96.7% of aborts CLIENT-HELD — the co-runner's L1 holding the exact
destination lines SBC wanted. We have already implicitly run "add a co-runner", and its
dominant effect was to BLOCK SBC, not feed it.
Why ZCache won on mixes and SBC may not: ZCache draws associativity globally from 64
replacement candidates; SBC pairs one hot set to one cold set and can move at most
`spare` lines. Weaker mechanism, tighter envelope.

### The throttle gap: we have a SELECTOR, not a PRECONDITION
What exists (source side, works, matches the paper):
  hotOK  = sat(qSet) >= tHi (31)          "is the source hot enough?"
  dssOK  = coldestLevel < tLo (16)        "is the destination cold?"
  DSS block list (2026-08-24)             "which other set should I try?"
What does not exist (destination side): any notion of FREE WAYS. The saturation counter
has no capacity term — a set that always hits decays to 0 and looks maximally cold while
being completely full. That was the 2026-08-24 DSS fix ("low miss-pressure != has room"),
which changed WHICH set is picked, not whether it has room. Nothing in the design carries
the `spare` term; parkCount counts guests, not empty ways.

The RTL already knows the difference and the decision discards it —
MSHR.scala:1617-1629:
  dstFree       = state === INVALID                       <- the ONLY real room
  dstEvictable  = !dirty && !clients.orR                  <- makes room by evicting
  dstReleasable = dirty && !clients.orR                   <- makes room by evicting

⚠️ 007 C2 -> 008 C2 -> 012 C2 progressively WIDENED that acceptance. 012 drove dirty
destination aborts 48,258 -> 0 with NO performance change. Those aborts WERE the throttle
— crude, accidental, expensive, but real back-pressure. We engineered it away, which is
why the envelope sweep now shows half the plane losing.

Two reasons the current signal can't carry a throttle yet:
  - M18: 21.4% of counter events are not accesses; inner-C write-backs cool a set by -1,
    so write-back traffic MANUFACTURES cold-looking destinations. Tap fix stays 🥇.
  - Coherence is invisible to it: clients.orR appears nowhere in the heat signal, so the
    counter structurally cannot predict the 96.7% client-held aborts — and the abort fires
    after the directory read and probe, so failing still costs.

Cheapest experiment (already named in CLAUDE.md): a runtime bit that accepts dstFree ONLY.
Makes `spare` a real requirement instead of something SBC fabricates by evicting a line
that was hitting.
